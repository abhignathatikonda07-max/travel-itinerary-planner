# Travel Itinerary Planner

A beginner-friendly, responsive full-stack travel planner. Registered travellers create their own trips, add day-by-day activities, organise destinations and dates, and calculate an estimated activity budget. Data is saved in Supabase PostgreSQL, not browser localStorage. No maps, booking integrations, AI APIs or paid APIs are required.

## Problem, users, scope
Travellers often lose their plans across messages and notes. This app puts dates, destinations, schedules and expected activity costs in one place. There is one role: **traveller**. Each account accesses only its own trips. Essential features: account registration/login, list/search trips, create/edit/delete trips, trip detail, create/edit/delete activities, chronological day grouping, notes, estimated cost total, logout. Future ideas: currency preferences, exports, offline sync, shared plans, maps. No real booking, currency conversion or travel recommendations are provided.

## Technology and architecture
HTML5 + CSS3 + vanilla browser JavaScript -> `fetch('/api/...')` -> Node.js / Express -> server-only Supabase clients -> Supabase Auth and PostgreSQL. `helmet` supplies security headers; `express-rate-limit` limits authentication requests; `dotenv` reads private server configuration. The browser stores only the access token in **sessionStorage** (lost when its tab session ends); passwords and service-role credentials never enter frontend files. Express validates the access token with Supabase Auth for each protected request and checks trip ownership before accessing data using the server-only privileged client. Database RLS is enabled without browser-facing policies: direct public/normal-user table access is denied. Never expose the service-role key. Supabase may require email confirmation; use the emailed link, or temporarily disable confirmation in Auth > Providers > Email for a controlled college demo. Do not disable it for production.

## Install and run (Windows PowerShell)
1. Install [VS Code](https://code.visualstudio.com/), [Node.js LTS](https://nodejs.org/en/download), and [Git](https://git-scm.com/downloads). Open VS Code > Terminal > New Terminal. Verify: `node -v`, `npm -v`, `git --version`. If not found, restart VS Code and check your PATH. Node 20+ is required.
2. Extract the supplied ZIP. In VS Code select File > Open Folder > `travel-itinerary-planner`. The ZIP already contains every application file. If manually recreating, create folders `frontend`, `backend/routes`, `backend/middleware`, `database`, and copy each corresponding file from the project.
3. At [Supabase](https://supabase.com/dashboard), create a free project. Save its database password privately. Wait for provisioning. Open **SQL Editor > New query**, paste the entire `database/schema.sql`, click **Run**. Confirm `trips` and `activities` in **Table Editor**. Do not manually insert an invalid user ID; accounts are created through Auth.
4. From **Project Settings > API** (or the current **API Keys** page), copy the project URL, the legacy `anon` key (or compatible publishable key), and legacy `service_role` secret key. The service-role credential MUST remain on the server. Create `backend/.env` by copying `backend/.env.example`. In a PowerShell terminal at the project root: `Copy-Item backend/.env.example backend/.env`. Replace all placeholder values. The app uses `SUPABASE_URL` for the project URL, `SUPABASE_ANON_KEY` for user auth, `SUPABASE_SERVICE_ROLE_KEY` for privileged backend database access, `PORT` for the local port, and `NODE_ENV` for the runtime environment. Do not put quotes around values unless needed. Never commit `.env`. **No credentials are supplied with this project.**
5. From project root run `cd backend`, then `npm install`. npm installs dependencies and creates/updates `package-lock.json`. Run `npm run check` for JavaScript syntax checks. If npm cannot connect, verify your internet or proxy and retry. On macOS/Linux use `cp backend/.env.example backend/.env` from the root instead of `Copy-Item`.
6. In `backend/` run `npm start` (or `npm run dev` for automatic restart). Expect `Travel Itinerary Planner: http://localhost:3000`. Open **http://localhost:3000** in a browser. Do not double-click `frontend/index.html` (API routes require Express).
7. Register using your own email and a password of at least eight characters. If confirmation is enabled, confirm by email, then log in. Create a trip, add dated activities, and observe their estimated cost sum. Use the search input on My trips.

`GET http://localhost:3000/api/health` confirms only that Express is running, **not** that the Supabase project can be reached. A successful register/login and creation/retrieval of a trip verifies end-to-end functionality. All dates in input are calendar dates. Cost is a number in the traveller's chosen currency (the app does not convert currencies); use the same currency across an itinerary.

## REST API
All requests and responses use JSON; on error: `{ "error": "Friendly message" }`. Protected requests require `Authorization: Bearer ACCESS_TOKEN`. Auth tokens come from login/registration, not from a user-supplied account ID.

| Method | Path | Body / query | Auth | Success |
|---|---|---|---|---|
| GET | `/api/health` | none | Public | 200 `{status,note}` |
| POST | `/api/auth/register` | `email,password` | Public; rate limited | 201 `{message,session}`; session can be null pending confirmation |
| POST | `/api/auth/login` | `email,password` | Public; rate limited | 200 `{access_token,email}` |
| GET | `/api/auth/me` | none | Signed in | 200 `{id,email}` |
| GET | `/api/trips` | none | Owner | 200 `{trips:[...]}` |
| POST | `/api/trips` | `title,destination,start_date,end_date,notes?` | Signed in | 201 `{trip}` |
| GET | `/api/trips/:id` | none | Owner | 200 `{trip,activities:[...]}` |
| PUT | `/api/trips/:id` | All trip fields | Owner | 200 `{trip}` |
| DELETE | `/api/trips/:id` | none | Owner | 200 `{message}`; activities cascade |
| POST | `/api/trips/:tripId/activities` | `title,activity_date,start_time?,location?,cost,notes?` | Owner | 201 `{activity}` |
| PUT | `/api/trips/:tripId/activities/:activityId` | All activity fields | Owner | 200 `{activity}` |
| DELETE | `/api/trips/:tripId/activities/:activityId` | none | Owner | 200 `{message}` |

Validation failures return 400; missing/invalid login 401; inaccessible trip/activity returns 404; a date edit that would exclude scheduled activities returns 409; excessive auth attempts return 429; unexpected server/database errors return a generic 500. Route ownership, schema constraints, trigger checks, and database foreign keys protect data integrity. A trip spans at most 61 calendar days. Dates must be within the trip, and activity cost is 0–10,000,000 with up to two decimal places. Notes and text are displayed with `textContent`, not interpreted as HTML.

## Manual testing checklist
- `/api/health` returns 200 with `status:ok` (server check only).
- Register with a valid email and password, confirm email if necessary, and log in: My trips appears.
- Blank fields, invalid dates, overlong text or negative cost: friendly rejection; bypassed browser checks still face backend validation.
- Create two trips: both persist after page reload and a fresh login; search finds matching title or destination and empty results display help text.
- Edit a trip: revised fields appear. Attempt to shorten it past an activity: 409 and no silent loss.
- Add activities with different dates and optional times: they are grouped by date and time. The sum is correct; edit and delete update it.
- Cancel delete confirmation: records remain. Confirm trip deletion: associated activities disappear too.
- Missing/invalid token: 401. User B attempting User A's trip ID: 404. User B's activity IDs under their own trip: 404; no cross-user edits.
- Login repeatedly with wrong credentials: eventually 429. Log out: private views disappear; revisiting requires login.
- Test on narrow mobile width: cards and forms stack, navigation remains usable.
- Stop backend: requests report connection errors. Wrong Supabase values: startup or auth/database requests fail; check credentials privately, never paste secrets into screenshots/issues.

No browser automation, live Supabase integration tests, or seeded user credentials are shipped. `npm run check` checks JavaScript syntax, not database connectivity.

## Troubleshooting
- `node`/`npm` not recognized: install Node.js LTS and reopen terminal.
- `Cannot find module`: run `npm install` inside `backend/`.
- `Configure SUPABASE...`: copy `.env.example` to `.env` and replace the sample values; run from `backend/`.
- 401 after sign-up: follow email confirmation link if enabled, then log in.
- `relation trips does not exist`: execute the SQL in the same Supabase project whose API URL is configured.
- Database permissions/key failure: confirm you used the server-only legacy `service_role` key, not the anon key, for `SUPABASE_SERVICE_ROLE_KEY`; keep it secret.
- Port already used: change `PORT=3001` and open localhost:3001.
- `Failed to fetch`: start Express, visit localhost rather than the HTML file, and check browser console/terminal.
- Supabase free project paused: resume it in your dashboard.
- Unrecognized API key type: use the compatible legacy `anon` and `service_role` keys as described above, or update SDK/config deliberately; do not paste any key in frontend code.

## Git and GitHub
From the **root** directory, create a new *empty* repository on [GitHub](https://github.com/) without auto-generated README. Check that `backend/.env` and `node_modules/` are ignored and `backend/.env.example` is included. Run:
```
git init
git status
git add .
git status
git commit -m "Build project"
git branch -M main
git remote add origin YOUR_GITHUB_REPOSITORY_URL
git push -u origin main
```
Replace `YOUR_GITHUB_REPOSITORY_URL` with your actual GitHub HTTPS/SSH URL. `git status` before committing must **not** list `.env`, local secrets, personal data or `node_modules`. After pushing, open GitHub and verify that README, frontend, backend, schema and package lock appear, but `.env` does not. Adding `.gitignore` after exposing a secret does NOT purge Git history: immediately rotate the leaked credential and remove it from repository history appropriately. Avoid committing sensitive exports or user information.

## Security and limitations
Passwords are managed by Supabase Auth. The frontend sends credentials only to the same-origin backend over HTTP locally; use HTTPS before deploying. `sessionStorage` is intentionally simple for a college demo and is not an XSS-resistant HttpOnly-cookie session; limit extensions and protect against script injection. Expired access tokens require re-login (there is no automatic refresh). No admin role, sharing, email recovery UI, actual travel bookings, automated currency conversion, live maps, or offline access. For production, consider CSRF-safe HttpOnly sessions, refresh-token rotation, stricter operational monitoring, account recovery, and automated integration tests.
